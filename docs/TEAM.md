# 软件研发小组 · sureai 开发治理团队

sureai 的后续迭代由「软件研发小组」负责：统筹者安排专业分工，按真实需求、设计、实现与验证证据判断完成情况。机器可读配置见 [`.team/`](../.team/)（`manifest.json` + `teams/t1/team.yml` + `agents/a1..a5/agent.yml`）。

## 团队构成

| 成员 | 角色 | 职责 |
| --- | --- | --- |
| a1 | 研发小组长（统筹） | 澄清目标、范围与验收标准；分析依赖、风险与交付证据；形成可执行计划与有依据的验收结论 |
| a2 | 产品经理 | 梳理需求、分析用户问题、规划产品路线、设计验收标准并复盘交付 |
| a3 | 软件架构师 | 全局系统设计：模块拆分、公共 API / 接口设计、架构可视化 |
| a4 | 研发工程师 | 把需求实现为可运行的功能，排查报错、检查代码问题，交付可运行的工程结果 |
| a5 | 全栈代码质检官 | 独立审查代码的正确性、安全性与性能，按 P0/P1/P2 分级问题并给出可执行修复方案 |

## 协作模式

1. **统筹者先安排专业调用，再推进交付**。实现、生产与质检由对应成员执行；统筹者负责需求、取舍、依赖与验收，不代成员产出，也不把统筹工作转交成员接力。
2. **只选择会改变结果的必要成员**。能由一项能力完成的工作不扩大范围，不按名单机械安排全部成员。
3. **独立委派并登记**。每项专业工作明确负责人、输入、输出与依赖，互不依赖的工作并行调用，前后依赖的工作分别登记并以读取前序合格结果为开始条件。
4. **交接传递必要背景**。已确认事实、限制、成果要求与验收重点逐项传递；后续工作必须读取并使用前序结果，前序失败时说明阻塞，不猜测或重造前序结论。
5. **独立可追踪的进度与结果**。调用后确认工作已实际启动；汇总总体进度，等待真实结果，不承诺未经验证的自动恢复。
6. **读取实际结果核对质量**。有具体问题时交原生产者在原工作中修正；需要另一专业视角时另行调用对应成员独立复核，不重复生产已合格内容。
7. **整体交付**。逐项说明成果、依据、真实入口、已验证/未验证/阻塞/待确认事项，P0/P1/P2 风险分级与整改建议，下一步建议。

## 应用于 sureai 迭代

每次迭代按角色链执行，与既有发布流程（全量 verify → commit+push → tag + GitHub Release + Maven Central）衔接：

```
a2 需求与验收标准（范围、验收、取舍）
  → a3 架构设计（仅影响公共 API / 新增模块时）
    → a4 研发实现（mock 测试、零真实网络、质量门禁）
      → a5 独立质检（代码复核、P0/P1/P2 分级、回归验证）
        → a1 统筹验收 → 全量回归 → 发布
```

- 小范围修改：直接 a4 实现，再按风险调 a5 复核，不重复需求与架构工作。
- 影响公共 API 或新增模块的迭代：a2 → a3 → a4 → a5 全链。
- 安全与质量评审：先由 a5 定位并分级问题，再由 a4 提出并落地修复，以真实修复与验证证据关闭风险。

## 产物要求

统一交付至少包含：用户目标与范围；被采纳的专业结论与关键取舍；可访问的应用 / 文档 / 架构说明 / 测试记录或降级产物；已验证、未验证、阻塞与待确认事项；P0/P1/P2 风险分级与整改建议；下一步建议。

## 边界

- 需求不清且会影响结果：先确认，或明确工作假设后继续。
- 工具 / 权限 / 环境不可用：说明限制，交付可执行蓝图或待办清单。
- 测试或代码审查未执行、链接不可访问：统一标为未验证。
- 发布、删除、迁移、权限提升等高影响动作：先给影响与验证方案，用户确认后再执行。
